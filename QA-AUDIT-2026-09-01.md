## 1. Executive summary

The detection stack does its job. On clean state an `easy` replay produces 821 scored
attempts, moves the threat band `calm → under_attack → resolved`, opens 521
incident-bearing events, fires all three Day-1 rules, and lands enforcement at exactly
the `2 / 10` the README promises. The 60× virtual clock is real and accurate — measured
at **58.5×**. That part works.

Everything the operator touches to *drive* that engine is broken. **Launch works once.**
After that, the demo cannot be restarted through the UI without a sequence no one would
guess:

> **Stop** leaves the UI reading `RUNNING` → **Reset** returns `HTTP 500` and changes
> nothing → a **second Stop** is the only thing that unfreezes the Launch button.
> Reproduced in the browser three times.

Underneath sit three independent defects that each, alone, would end a demo. Reset is a
hard `500` in the documented Redis configuration, so the only mechanism designed to make
the demo repeatable never runs. The replay's terminal state is never published to the
event stream and nothing polls for it, so a completed run renders forever as
`RUNNING (820/821)` with every control disabled — this is precisely the "freeze around
820", and the number is not a coincidence: the `easy` tier is exactly 821 events. And
Redis idempotency keys with a **~24-hour TTL** mean a second run of the same tier scores
821 attempts while emitting **zero** events to the dashboard.

Separately and most seriously for a live demo: during a 60× run in the browser, the
scorer **wedged completely** — stuck at 743/821, burning 100% of one core, with
`/healthz` and `/v1/score` both timing out. It required a kill. The trigger was not
isolated; see AUDIT-006, which says so rather than guessing.

## 3. The six that end the demo

### AUDIT-001 — Reset returns HTTP 500 in the documented configuration
**CRITICAL · Backend · Redis · `services/scorer/replay.py:89`**

- **Expected** — Per `08-UIUX-SPEC` §6.12, "Reset is required, not convenient": it must
  clear the window store, threat rollup, Layer 2, incidents and policy engine so the demo
  can run more than once per process.
- **Actual** — `POST /v1/replay/reset` returns **500 on every call** whenever Redis is the
  window-store backend — which is the configuration the README instructs
  (`docker compose up -d redis`) and which `.env` sets.
- **Root cause** — `ReplayDriver.reset()` calls `self._state.window_store.clear()` on its
  *first* line. `clear()` is not on the `WindowStore` protocol; only `InMemoryWindowStore`
  implements it. Because it throws first, **nothing else in reset ever runs** — `threat`,
  `layer2`, `incidents`, `policy_engine` and the status are all left untouched.

```
File "services/scorer/replay.py", line 89, in reset
    self._state.window_store.clear()
AttributeError: 'RedisWindowStore' object has no attribute 'clear'
```

- **Missing** — `clear()` on the `WindowStore` protocol and a Redis implementation.
- **Recommended fix** — Add `clear()` to the protocol and both backends (scoped `SCAN` +
  `UNLINK` over `tg:{merchant}:*`, never `FLUSHDB`). Reorder `reset()` so store-clearing
  is not a single point of total failure, and have the route report which layers cleared.

### AUDIT-002 — A finished run renders forever as `RUNNING (820/821)`
**CRITICAL · State synchronisation · `App.jsx:41`, `DemoControlStrip.jsx`, `replay.py:145-153`**

- **Expected** — On completion the strip reads `finished (821/821)` and Launch re-enables.
- **Actual** — The strip freezes one event short of the total and **Launch, tier and speed
  stay disabled permanently**. `easy` @ seed 42 is exactly **821 events**, so the terminal
  display is always `820/821`. The `medium` form is `700/701`.
- **Root cause** — `replayStatus` has only two sources: the response to a button click, and
  `latest.replay` piggybacked on SSE events (`App.jsx:41`). The driver writes `sent=i`
  *after* publishing event `i`, so the last event ever published carries `sent = total−1`.
  The subsequent `finished` transition publishes nothing, and **nothing in the dashboard
  ever calls `GET /v1/replay/status`** — the endpoint exists and is correct, but is dead
  code from the UI's perspective.

```
Frontend State           : running  · 700 / 701
Backend State            : finished · 701 / 701
API State                : finished · 701 / 701   (GET /v1/replay/status)
Rendered Value           : "REPLAY: RUNNING (700/701)"
Expected Value           : "REPLAY: FINISHED (701/701)"
First Point of Divergence: the terminal status transition in ReplayDriver.run()
                           is never published to the event bus, and no poller
                           closes the gap.
```

Verified in-browser with Launch disabled and the tier select showing `easy` after a
`medium` run.

- **Recommended fix** — Poll `GET /v1/replay/status` from the DC strip on a 1s interval
  whenever state is `running`, **and** publish a terminal control frame on the bus. Do
  both — the poll is the safety net for a dead task, the frame is the low-latency path.

### AUDIT-003 — Stop returns the snapshot from before the stop
**CRITICAL · API · `services/scorer/routes_replay.py:58-61`**

- **Expected** — Clicking Stop leaves the UI showing `stopped` with Launch re-enabled.
- **Actual** — The UI still reads `RUNNING` with every control disabled. The backend stops
  within ~2s; the UI never learns.
- **Root cause** — `replay_stop` sets a flag then immediately serialises
  `status.to_dict()`. There is no `await` between them, so the loop has had no chance to
  observe the flag — the handler returns the still-`running` status, and the strip stores
  it via `onReplayStatus(data)`.

```
during run  /status : running:7/701
POST /stop -> HTTP 200 body=running:11/701   <-- this is what the UI renders
/status 1.5s later  : stopped:12/701

# browser, clean run:
UI  : REPLAY: RUNNING (29/821)   Launch disabled=true
API : stopped : 30/821
```

- **Consequence** — Combined with AUDIT-001, the operator is trapped: Stop looks like it
  failed, Reset 500s, and only a *second* Stop (which now returns the true `stopped`)
  releases the UI. Clicking Stop twice is an undocumented workaround, not a feature.
- **Recommended fix** — Make stop await actual loop acknowledgement (an `asyncio.Event`
  the loop sets on exit, with a short timeout), or return `202` with a `stopping` state
  and let the AUDIT-002 status poll resolve it.

### AUDIT-004 — Reset-while-running reports success while the backend keeps scoring
**CRITICAL · State synchronisation · `services/scorer/replay.py:84-99`**

- **Expected** — Reset either stops the run first, or refuses.
- **Actual** — On the in-memory backend, Reset during a run returns **`200 {state:"idle"}`**
  — the UI shows idle and re-enables Launch — while `run()` continues untouched. 200 ms
  later the loop overwrites the status back to `running`. On Redis it 500s instead and the
  run also continues.

```
# in-memory backend
running: running:7/821
reset -> HTTP 200 body=idle:0/0
+0.2s : running:13/821          <-- the loop overwrote the reset

# redis backend
before reset : running:6/701
POST /reset  -> HTTP 500
+3.3s        : running:19/701
>>> BACKEND KEPT RUNNING THROUGH RESET
```

- **Worse** — `reset()` wipes `window_store`, `threat`, `layer2`, `incidents` and
  `policy_engine` *mid-run*. Every remaining attempt is then scored against a half-erased
  feature store — silently wrong output, not an error. There is also a real window in
  which `status` reads `idle` while `run()` is alive; a Launch landing there passes the
  409 guard and creates a **second concurrent driver** sharing one `VirtualClock`. This
  could not be triggered through HTTP timing, so it is recorded as code-evident rather
  than confirmed.
- **Recommended fix** — Reset must cancel `state.replay_task` and await its completion
  before touching any state. Guard it the same way start is guarded.

### AUDIT-005 — The second run of a tier is invisible for the next 24 hours
**CRITICAL · Redis · Data · `packages/features/windows.lua`, `services/scorer/scoring.py:489`**

- **Expected** — Re-running a tier replays the attack and drives the dashboard again.
- **Actual** — A second `easy` run in the same process reported **`finished 821/821` while
  publishing zero SSE events**. The dashboard shows nothing at all — no ticker rows, no
  threat change, no incidents.
- **Root cause** — Replay `attempt_uid`s and payload digests are deterministic per
  `(tier, seed)` by design. `windows.lua` does `SET NX PX` on `tg:{m}:idem:{digest}`; a hit
  returns immediately with every window untouched. `score_attempt` then takes the
  stored-decision early return and **skips the spool append and the SSE publish**.
  Measured TTL on those keys: `86,198,096 ms ≈ 23.9 hours`. One run leaves **3,194 keys**
  behind. The only thing that clears them is Reset — which is AUDIT-001.

**Cross-tier contamination.** All four tiers share the same seeded legitimate baseline, so
this affects *different* tiers too. Measured exactly on `hard` after an `easy` run:

```
BEFORE hard: redis_idem=1444  db_auth_attempt=1444
AFTER  hard: redis_idem=1873  db_auth_attempt=1873
sent=508, new=429  ->  79 of 508 events (15.6%) SILENTLY SWALLOWED
SSE events received: 429

resulting run       : threat_state 100% calm, 0 incidents, 0 enforcement
comparable clean run: 303 under_attack events, 255 incidents, enforcement 6/10
```

Those 79 are precisely the pre-attack warm-up baseline, so the run begins cold, directly
inside the attack.

- **Recommended fix** — Namespace replay keys by run: prefix with a per-run id, or fold
  `epoch_ms`/run-uuid into `idem_digest` for replay-sourced attempts. Then make Reset
  actually delete them. Also shorten the idem TTL — 24h is a production-traffic figure
  applied to a demo generator.

### AUDIT-006 — The scorer wedges mid-run and stops answering entirely
**CRITICAL · Backend · Reliability · root cause NOT determined**

- **Expected** — A 60× `easy` run completes in ~180s and the service stays responsive.
- **Actual** — Observed twice.
  - **Run A** (browser attached, port 8080): froze at `743/821`, `virtual_time_ms` stuck at
    7,157,521 for 110+ seconds, then `/healthz`, `/v1/score` and `/v1/replay/status`
    **all timed out** while the process burned **98% of one core**.
  - **Run B** (port 8081): froze at `0/821` with zero events emitted.
  - Both required a kill.
- **Not pacing** — Ruled out by measurement: the largest inter-event sleep at 60× in this
  stream is **4.6s**, and the gap at the freeze point was **1.25s**. The loop was wedged,
  not waiting.

```
17:30:56  sent=742
17:31:01  sent=743
  ... 27 consecutive samples, all 743 ...
healthz         : 000 in 6.004569s    (timeout)
POST /v1/score  : 000 in 10.001897s   (timeout)
PID 29216  cpu_4s=3.91s => 98% of one core, WS=9MB
redis-cli PING         -> PONG    (Redis healthy)
sqlite BEGIN IMMEDIATE -> 0.00s   (DB not locked)
```

- **Root cause** — **Not conclusively determined.** The leading hypothesis was tested and
  *disproved*: a controlled run against a copy of the same 29.6 MB spool and the same DB
  finished cleanly in 192.5s, as did a fresh-spool run (192.6s). Redis, SQLite locking and
  event-stream backpressure were each checked and cleared. What is established: the only
  `await` in the scoring hot path is the terminal `event_bus.publish`; the event loop
  stayed schedulable in Run B while the replay task did not advance; and the process spins
  rather than idles. Most likely a fault in the replay task or the spool/SQLite drainer
  subsystem — see AUDIT-012, where two crashes landed in exactly that thread.
- **Recommended fix** — Do not ship a live 60× demo until this is bisected. As mitigation,
  AUDIT-007's watchdog would at least surface it instead of presenting it as a frozen
  counter. Add a per-attempt timeout in the replay loop and a heartbeat that marks the run
  `failed` when no event advances within N seconds.

## 4. High severity

### AUDIT-007 — Any replay-task failure is swallowed and shows as a frozen counter
**HIGH · Architecture · `services/scorer/replay.py:101`, `routes_replay.py:54`**

`ReplayDriver.run()` has no `try/except`, and `state.replay_task` is stored but never
awaited or inspected. Because the task object stays referenced, asyncio never even emits
its "Task exception was never retrieved" warning — the failure is invisible in the logs
(confirmed: a run stuck at 0/821 produced no log line at all).

Whatever goes wrong — an exception, a cancellation, the AUDIT-006 wedge — the status stays
`running` forever, so the UI disables Launch forever. **This is the amplifier that turns
every backend hiccup into a dead demo.**

**Fix** — Wrap the loop body; on exception set `state="failed"` with the reason, log it,
and surface it in the strip. Add a done-callback on `replay_task` that retrieves the
exception.

### AUDIT-008 — The Incidents screen is unreachable while incidents are open
**HIGH · Frontend · `App.jsx:64`**

The screen renders its empty state — *"No incidents. Baseline learned while traffic is
nominal"* — while `GET /v1/incidents` returns **8 incidents, all `ESCALATED`**.

`liveIncidentId` scans only the in-memory SSE array for an event carrying a non-`CLOSED`
incident. `GET /v1/incidents` is implemented, authenticated and correct — and **the
dashboard never calls it** (`grep` finds only `/v1/incidents/{id}`). So once the attack
scrolls out of the 200-event buffer, or after any refresh, D3 — described in the README as
"the centre of gravity" — becomes unreachable even though the data is one request away.

**Fix** — Have the Incidents route fetch `GET /v1/incidents` and pick the newest open one,
using the SSE buffer only as a live accelerator.

### AUDIT-009 — Refresh mid-attack shows an all-clear dashboard
**HIGH · State synchronisation · `services/dashboard/src/hooks/useEventStream.js`**

Reloading during a live `medium` run rendered `CALM`, `ENFORCEMENT 0 / 10`,
`CARDS PER IP · TOP = 1` — while the backend's own recent buffer held 119 `under_attack`
events, 109 incident-bearing events and a peak `distinct_cards_per_ip_5m` of **41**.

`useEventStream` mounts with `events: []` and only calls `/v1/stream/recent` from
`startPolling()` — the SSE-*error* path. On a normal mount it never back-fills, so every
derived value (threat band, all four tiles, rail, ticker, incident lookup) is computed from
an empty array until fresh events trickle in.

**Fix** — Call `/v1/stream/recent` once on mount before opening the EventSource. The
endpoint and its 200-event buffer already exist for exactly this.

### AUDIT-010 — The Day-2 end-to-end gate fails in the suite and passes alone
**HIGH · Testing · `tests/acceptance/test_day2_e2e.py:161`, `_spawn` at :81**

Two full runs, identical result: **1 failed, 381 passed, 2 skipped, 2 xfailed** (196s,
190s). The single failure is the acceptance gate for the demo's own headline path.

```
tests/acceptance/test_day2_e2e.py:161
E   AssertionError: none of R1/R2/R3 fired during the easy-tier replay; saw rules: set()

# same test, run alone:            1 passed in 6.62s
# same test, alone + shared Redis: 1 passed in 9.23s
```

Order-dependent, reproducible across both suite runs. The mechanism is not fully pinned,
but the clear structural candidate is environment leakage: `create_app`'s lifespan calls
`load_env_file()`, which loads the repo-root `.env` into the *pytest process's*
`os.environ` and is guarded by a module-level once-flag; `test_day2_e2e._spawn` then does
`full_env = dict(os.environ)` and hands the whole thing to the subprocess. So a test that
ran earlier can change this test's backend configuration. Isolated runs never see it —
exactly the observed signature.

**Fix** — Have `_spawn` pass an explicit allow-listed env rather than a copy of
`os.environ`. Add an autouse fixture that snapshots and restores `os.environ` plus
`env._loaded`. Then re-run to confirm: this is the one test that would have caught most of
the criticals above, so it must be trustworthy *before* the fixes land.

### AUDIT-011 — D6 shows the model at 0.000 on the easiest tier, with no caveat
**HIGH · UX · Honesty · `screens/D6Metrics.jsx`, `components/charts/BarRow.jsx`**

The Act-Two headline chart renders `l1-lgbm-v1 · easy = 0.000` directly above
`B0 — live rules · easy = 0.997`. To a judge that reads as "the model is beaten by three
hand-written rules on the easiest attack."

The artifact itself disagrees. **All eight `recall_at_target_fpr` entries in
`eval/outputs/d6.json` carry `"resolvable": false`** (`n_neg` = 221 or 316 — too few
negatives to resolve FPR 1e-3). `grep` confirms the string `resolvable` appears **nowhere**
in the dashboard source. `BarRow` renders every value as a confident `value.toFixed(3)`.

```
l1-lgbm-v1     easy     recall=0.0      resolvable=False  n_neg=221
l1-lgbm-v1     medium   recall=0.9729   resolvable=False  n_neg=221
l1-lgbm-v1     hard     recall=0.7317   resolvable=False  n_neg=316
l1-lgbm-v1     evasive  recall=0.3905   resolvable=False  n_neg=221
rules-only-v0  easy     recall=0.9967   resolvable=False  n_neg=221
```

UIUX §6.13 is explicit that the evasive bar gets no cosmetic softening — that is about not
flattering a *real* number. Rendering an unresolvable metric as `0.000` is the opposite
failure: it fabricates a precise, unflattering number the harness explicitly declines to
assert.

**Fix** — Render `n/a — not resolvable at n_neg=221` for any entry with
`resolvable: false`, and lead the block with a metric that *is* resolvable at this sample
size (`ap_raw`, where the model reads 0.79–0.997 across tiers).

### AUDIT-012 — Two hard crashes, both in the drainer thread
**HIGH · Backend · `packages/storage/drainer.py:49-118`, `packages/storage/db.py:21`**

Two scorer processes died with **exit code 139 (SIGSEGV)**. `faulthandler` caught both, and
both landed in the `Drainer._run` thread inside `drain_once()`:

```
Thread 0x00003308:
  File "packages/storage/db.py", line 21 in connect      # PRAGMA journal_mode = WAL
Windows fatal exception: access violation

Thread 0x00005c9c:
  File "pathlib/_local.py"                               # drainer.py:50 _spool_path.exists()
Windows fatal exception: access violation
```

**Contributing design** — `Drainer._run` polls every **50 ms**, and `drain_once()` opens a
brand-new SQLite connection each time and re-issues `PRAGMA journal_mode = WAL` — **20
connections and 20 journal-mode switches per second**, forever, whether or not there is
anything to drain.

**Caveat, stated plainly** — Both crashing processes ran under
`faulthandler.dump_traceback_later(repeat=True)`, introduced by this audit; the
uninstrumented process hung (AUDIT-006) rather than crashing. The diagnostic cannot be
fully excluded as a contributor.

**Fix** — Hold one long-lived drainer connection; set `journal_mode` once at schema init,
not per connection. Skip the DB entirely when the spool offset has not moved.

## 8. What genuinely passed

- **The detection stack.** On clean state, all four tiers generate, replay and score
  deterministically. Rules, model, Layer 2, incident state machine and policy engine all
  produce coherent output.
- **Virtual clock fidelity.** 58.5× measured against 60× nominal; `speed=0` and `speed=60`
  agree; `test_time_travel` passes.
- **Throughput.** At `speed=0`, 821 attempts scored in under 2 seconds (~450/s) with full
  Layer-2 folding.
- **381 of 382 tests pass**, including durability-under-hard-kill, cross-interpreter
  determinism, the Redis-vs-pandas window differential, calibration, and the simulator
  import-closure safety scan.
- **Auth on the data endpoints.** `/v1/incidents` and `/v1/replay/start` correctly 401
  without a key; API keys in both `.env` files match the seeded merchant hash.
- **Accessibility fundamentals in the threat band.** Four distinct glyphs plus uppercase
  labels; colour genuinely never load-bearing, exactly as UIUX §2.5 requires.
- **A clean console.** Across the whole browser session: no JS errors, no unhandled
  rejections, no React warnings.
- **Graceful degradation paths exist and are wired** — SSE→polling→SSE, rules-only shed,
  fail-open ladder, in-memory window-store fallback.

## 9. Blocked / untested, and why

- **Storefront screens S1/S3/S5/S6/S7** — the browser extension lacked host permission for
  `localhost:5173`. Code-reviewed only; that is how AUDIT-019 was found.
- **D3 confirm / resolve** — unreachable because of AUDIT-008. The API endpoints exist and
  are authenticated; their behaviour is unverified.
- **Fault injection** — killing Redis mid-run, killing the scorer mid-run, and
  network-partitioning SSE were not exercised. The fallback code paths exist and their unit
  tests pass, but live degradation was not observed.
- **`POST /v1/outcome`** — requires HMAC signing with the outcome secret. Its acceptance
  tests pass; not exercised live.
- **Negative-control scenarios** (`flash_sale`, `cgnat`, `nri_traffic`, …) — covered by the
  harness, not by this audit; the DC strip has no selector for them.
- **Long-run stability** — the longest observed run was ~193s. Memory was flat (9 MB
  working set), but no multi-hour soak was attempted.
- **Accessibility beyond the threat band** — no screen-reader pass, no keyboard-only
  traversal, no contrast measurement.
- **The root cause of AUDIT-006** — two hypotheses tested and disproved; investigation
  stopped rather than continuing to guess.

## 11. Notes for whoever fixes this

**Clear Redis between every verification run.** This is the single biggest time sink. Until
AUDIT-005 is fixed, a second replay of the same tier silently no-ops for ~24 hours. Re-run
`easy` to check a fix, see zero events, and you will conclude you broke something. Before
each check:

```
docker exec tollgate-redis-1 redis-cli FLUSHDB       # or use a fresh logical DB
```

**Do not claim AUDIT-006 is fixed without reproducing it first.** Root cause is undetermined
and the obvious hypothesis was disproved. A plausible-looking patch there will produce a
confident "fixed" with nothing behind it.

**Get the suite green before landing fixes.** `test_day2_e2e` (AUDIT-010) is the gate for
most of the P0 findings; it cannot validate them while it is order-dependent.

## 12. Final verdict

**NOT READY.** Not because the product does not work — the hard part, the detection stack,
demonstrably does. It is not ready because the surface in front of it cannot be driven
twice in a row, and every one of its failure modes presents as a plausible-looking frozen
number rather than an error.

Three things block a live demo outright. The run never reports completion, so Launch
disables itself permanently after one use. Reset — the mechanism explicitly designed to
make the demo repeatable — is a hard `500` in the configuration the README tells you to
use. And a repeat run of any tier silently scores everything and shows nothing, for 24
hours. Those three compound: the natural recovery sequence a presenter would try is exactly
the sequence that fails.

Underneath them, AUDIT-006 is the one to fix first and trust last. A scorer that stops
answering `/healthz` mid-demo while its dashboard displays a confident, stationary counter
is the worst possible failure in front of an audience, and its trigger is unknown.

The good news is that the P0 list is small and mostly mechanical: one missing method, one
status poll, one acknowledgement handshake, one key namespace. None of it requires
rethinking the architecture. The engine is sound; the instrument panel is wired to the
wrong terminals.
